## 第一部分 · 我们现在到底在哪

### 1.1 用工程界通行的分级说话

| 维度 | 分级 | 判定依据（可核对） |
|---|---|---|
| 技术成熟度 TRL | **TRL 4→5 之间** | 组件在实验室环境集成验证通过（1010+316 测试全绿、端到端跑通），但**从未在真实用户的真实工作流里连续运行过一周** |
| 产品成熟度 | **可用原型（Working Prototype）**，非 MVP | MVP 的定义是「最小可行」——可行意味着有人愿意持续用。目前没有任何一个非开发者用户的留存数据 |
| 学术成熟度 | **Workshop paper 素材，够不上主会** | 有系统贡献、有诚实的方法论设计，但**零实证结果**：没有数据集、没有相关性验证、没有用户研究 |
| 商业成熟度 | **Pre-Problem-Solution Fit** | 尚未验证「有人真的因为选错 Agent 而痛到愿意付费」 |

### 1.2 已经真实存在、可以拿出去讲的东西

这些我逐行读过代码、跑过实测，不是文档里的说法：

1. **机器可核验的双证据链**（`sandbox/runner.py` + `sandbox/security_scan.py`）。
   实测：一段测试 4/4 全过的代码被静态扫描抓出 3 处高危（硬编码凭据、
   `shell=True`、`eval`）。这是全项目**唯一无法被质疑的部分**——
   它不依赖任何模型判断。
2. **拒绝造分的工程纪律**。`MockJudgeBackend.available` 恒 `False` 且
   `complete()` 必抛；离线回退不再用 agentId 哈希；零证据时给中性基线并
   标注「不可评」。这种自我约束在同类作品里极少见。
3. **12 道带反注水探针的工种题**。手工资产，有原创性。
4. **多 Agent 编排器**（`squadOrchestration.ts`）显式对治 MAST(arXiv:2503.13657)
   的 verification gap，设计水平高于评测层本身。
5. **完整的工程门禁**：双 tsconfig 严格类型、1010 前端 + 316 后端测试、
   隐私 grep、i18n parity、CI。

### 1.3 但这些都还不是「产品」

一个残酷的检验：**如果今天把这个软件给 100 个不认识你的职场人，
会发生什么？**

我的预测（基于对代码的阅读）：
- 约 70 人卡在安装（要装 Node、pnpm、Python、可选 uv、还要配 JUDGE_BASE_URL 和 API key）；
- 剩下 30 人里约 25 人打开后不知道该干什么（首屏是 Chat，不是「描述你的工作」）；
- 剩下 5 人跑通一次评测，看到六维雷达图，觉得「挺酷」，然后**再也不打开**——
  因为他们并没有「我要在 5 个 Agent 里选一个」这个待办事项。

**最后这一条才是致命的。** 前两条是工程问题，砸时间就能解决；
第三条是产品问题：我们造了一个精密的答案，但还没证明有人天天在问这个问题。

## 第二部分 · 学术视角的批判

### 2.1 先看清楚我们站在谁旁边

2025-2026 这一年，「用真实工作任务评测 Agent」已经从空白变成拥挤赛道：

| 工作 | 做法 | 与我们的关系 |
|---|---|---|
| **GDPval**（OpenAI, 2025）[2](https://openreview.net/forum?id=hcuEdq6eKD) | 1320 个任务、44 个职业、覆盖美国 GDP 前 9 大行业，行业专家（平均 14 年经验）出题并盲审打分，开源 220 题 gold 子集 + 公开自动评分服务 | **最强的正面竞争**。它把「真实工作」这个词占住了，而且有 OpenAI 的资源做专家标注 |
| **TheAgentCompany**（NeurIPS 2025 D&B）[4](https://arxiv.org/abs/2412.14161) | 自建一个软件公司环境，agent 要浏览网页、写代码、与「同事」沟通；最佳模型完整完成率约 30% | 证明了「真实工作场景」远未饱和；也证明了环境仿真的工程量有多大 |
| **CLASSIC**（enterprise agent benchmark）[10](https://openreview.net/pdf?id=RQjUpeINII) | 2133 条真实企业对话、423 个工作流、7 个领域，五维度：Cost / Latency / Accuracy / Stability / Security | **与我们六维高度重叠**，且用的是真实企业数据。这是最直接的学术撞车 |
| **PAL**（ICLR 2025）[1](https://openreview.net/pdf?id=1kFDrYCuSu) / **PERSONA** / **Pairwise Calibrated Rewards**[5](https://arxiv.org/abs/2506.06298) | 多元对齐：不假设单一普适偏好，为每个用户学个性化奖励模型；把标注者分歧当作信息而非噪声 | **我们「主观榜」理念的学术母体**。但他们已经做到了「学个性化奖励模型」，我们还停留在「让用户手动拖排序」 |
| **Rating Roulette**（EMNLP 2025 Findings）[1](https://aclanthology.org/2025.findings-emnlp.1361.pdf) | 实测 LLM 判分的自一致性与人机一致性：MT-bench 上人类之间 α 仅 0.478，GPT-4 vs 人类 α 0.396；accuracy 0.827 却掩盖了这一点 | **我们元评估的直接依据，也是对我们的警告** |
| **No Free Labels**（arXiv:2503.05061）[3](https://arxiv.org/html/2503.05061v1) | 判官答不出的题就judge不准；给人工参考答案能显著提升一致性并降低自偏好 | 我们的 `_REFERENCES` 参考答案锚定做对了，但只覆盖 12 题 |

**结论：单纯的「用真实任务评 Agent」已经不是 novelty 了。** 如果论文按这个角度投，
审稿人第一句就是「与 GDPval / TheAgentCompany / CLASSIC 的区别是什么」。

### 2.2 那我们真正可能的学术贡献点在哪

我认为只有一条路走得通，而且它恰好是上述所有工作**都没做**的：

> **个体层面的准入决策效度**（individual-level admission validity）：
> 一个由「使用者自己的价值排序」参数化的评测结论，
> 能否预测**该使用者**在后续真实协作中的满意度与返工率？

拆开说，这里面有三个可发表的子问题：

**（A）个性化排序的预测效度**
GDPval 与 CLASSIC 给的是群体平均的能力分。但真实的选型决策是个体的：
同一个 agent，重视「一次做对」的人和重视「便宜够用」的人应该选不同的。
我们的 `user_fit = Σ(radar/5 × weight)` 加上主观榜重排，本质上是一个
**人工指定的个性化效用函数**。学术问题是：这个效用函数比群体平均分
更能预测个体满意度吗？如果能，能多多少（ΔSpearman ρ）？
如果不能——那就是一个同样有价值的负面结果，而且诚实报告负面结果
本身就是我们「诚实性」定位的最好背书。

**（B）人机协同收敛过程的度量**
`convergence/` 那一层现在度量的是「人机对齐过程」，但用的是
**64 维词袋哈希**（`encoder.py`），同义改写会落到完全不同的向量上。
这个度量目前站不住。但问题本身是好问题：
「使用者需要几轮才能把自己的意图讲清楚」是选型的关键成本项，
现有 benchmark 全是 one-shot（GDPval 论文自己承认这是局限[3](https://the-decoder.com/openai-says-top-ai-models-are-reaching-expert-territory-on-real-world-knowledge-work/)）。
**这是我们相对 GDPval 唯一的结构性优势：我们有多轮交互的真实数据。**

**（C）低成本准入评审的经济性**
「花 12 道题 + 3 次 ensemble 的成本，能避免多大的选错代价」——
这是一个可以量化的决策论问题，也是企业最关心的问题。
现在没人做，因为需要既有评测数据又有上线后表现数据。
我们的 `workEvaluationLoop` 回流刚好产生这份配对数据。

### 2.3 现在必须承认的方法论硬伤（按严重程度）

**① 零预测效度证据 —— 这是唯一真正致命的一条**

README 已经诚实写了「当前指标验证的是稳定性，尚未验证预测有效性」。
但这句话的分量可能被低估了：**没有预测效度，整套评分在科学上就只是一个
自洽的记分规则，而不是一个测量工具。** 稳定但无效的测量（例如用鞋码预测智商，
测十次都一样稳）没有任何价值。

这也是把项目从玩具变成科学的唯一门槛。见第四部分的验证实验设计。

**② 题量不足以支撑维度分数**

每个工种只有 4 道题，却要撑起 5 个 craft 维 + 6 个通用维。
经典测量学的经验值是：要让一个维度的 Cronbach α ≥ 0.8，
通常需要 **6–10 个独立题项**。当前 `code_runnability` 的分数可能只来自 1–2 题
——单题分数的信度约等于抛硬币加权。

**可核对的推论**：现在如果同一个 agent 做两套不同的 4 题，
分差很可能超过 1.0（满分 5）。**这个实验今天就能做，成本只有 API 费用。**
建议立刻做，因为如果结果真的这么差，后面所有工作的优先级都要重排。

**③ 「同题同标尺」与「污染」的内在矛盾**

题库是公开端点（`GET /api/craft-tasks`）。一旦这个项目有影响力，
题目会立刻进入下一代模型的训练数据。GDPval 的应对是保留私有 held-out 子集；
SWE-bench 的教训是公开题库两年后基本失效（该榜单的抗污染评分已跌到 3/10[1](https://o-mega.ai/articles/top-50-ai-model-evals-full-list-of-benchmarks-october-2025)）。

我们目前**没有任何抗污染设计**。参考答案不外发是对的，但题面本身是公开的。

**④ 元评估的阈值口径曾经用错（已修）**

`META_JUDGE_DEFAULTS.acceptableThreshold = 0.67` 原本注释为
「Krippendorff α 分级」，却被用来判断**未经随机校正的 accuracy**。
二值判断的随机基线就是 0.5，accuracy 0.67 只比抛硬币好一点点。
Rating Roulette 实测的正是这个高估效应：MT-bench 上人类之间
accuracy 0.827、α 却只有 0.478[1](https://aclanthology.org/2025.findings-emnlp.1361.pdf)。
**本次已修**：accuracy 下限提到 0.75 且仅作参考，准入判据改为 α ≥ 0.67。

**⑤ 裁判能力上限压制被评方能力上限**

No Free Labels 证明：judge 答不出的题就判不准[3](https://arxiv.org/html/2503.05061v1)。
我们让 `qwen-plus` 级别的裁判去评 `code_boss_system`（设计可崩溃恢复的任务队列）
这种题，裁判自己未必能给出满分答案。这意味着**顶部区分度会塌陷**——
所有强 agent 都会拿到相近的高分。

缓解手段我们已经有一半（参考答案锚定），但只覆盖 12 题且是我们自己写的，
不是「人工验证的满分基准」意义上的 gold。

**⑥ 二值化丢信息 + 样本量**

元评估把 MVP/OBSERVE/FIRED 压成二值，这是我刻意的选择（序数一致性需要
高一个数量级的样本），但代价是无法诊断「MVP 与 OBSERVE 的边界画得准不准」。
而且 `minSamplesForDrift = 20` 对漂移检测来说过于宽松——
20 个样本切两半各 10 个，单个样本翻转就能造成 10% 的 delta 抖动，
默认 0.15 的阈值意味着 2 个样本翻转就报「漂移」。**建议提到 50。**

**⑦ 收敛层的语义编码不成立**（见 2.2-B）

**⑧ Elo 的前提假设未检验**

`scoring/elo.py` 假设可传递性与对局独立性。人类偏好经常违反可传递性
（A>B, B>C, C>A），Chatbot Arena 靠海量对局稀释这个问题，
我们单用户几十次对局根本压不住。**当前 Elo 数字不应对外展示为「排名」。**

## 第三部分 · 商业视角的批判

### 3.1 最难回答的问题：这是维生素还是止痛药

我把话说直白：**「选错 Agent」目前对绝大多数个人用户还不是痛点。**

理由很实在——普通职场人现在不是在 50 个 Agent 里挑，他们是在
「用不用 AI」和「用 ChatGPT 还是用公司发的那个」之间挑。选择过载这个前提，
在 C 端**还没有真正到来**。我们是在为一个尚未普遍发生的痛点提前造解药。

这不必然是坏事——提前一步是先发优势，提前三步是先烈。
问题在于我们要诚实判断自己提前了几步，并据此决定烧多少钱、等多久。

**反过来，B 端的痛点已经真实存在了**：
企业引入 Agent 要过合规、要定责任、要向上汇报「为什么选它」。
「带证据的准入评审报告」在 B 端是刚需文档，在 C 端只是个好看的图。

**因此我的判断很明确：把 B 端当主线，C 端当获客漏斗和数据来源。**
这与当前代码的重心（桌面端、单机、个人化老板原型）**是冲突的**，
需要一次明确的转向决策。

### 3.2 ICP 画像：现在太模糊

README 说「为普通职场人」。这个定位在商业上几乎不可执行：
「普通职场人」不是一个可触达、可付费、可复购的群体。

三个候选 ICP，我建议按这个优先级：

| ICP | 痛点强度 | 付费能力 | 可触达性 | 我的判断 |
|---|---|---|---|---|
| **A. 企业 AI 平台/中台负责人**（要为全公司选型并背责任） | ★★★★★ | ★★★★★ | ★★☆ | **主线**。他们需要的正是「可复核的准入报告」 |
| **B. AI Agent 开发者/团队**（要证明自家 agent 比对手好） | ★★★★ | ★★★ | ★★★★ | **次线**，也是最好的冷启动来源——他们有动力主动来跑分 |
| **C. 个人知识工作者** | ★★ | ★ | ★★★★★ | **漏斗与数据源**，不作为收入预期 |

注意 B 的战略价值：**被评测方主动来跑分，是评测平台唯一的规模化冷启动路径。**
Chatbot Arena 靠的是用户投票，SWE-bench 靠的是模型厂自己刷榜。
我们如果能让 Agent 作者主动来「考公务员」，题库和数据就自己滚起来了。

### 3.3 竞争格局：我们最容易被谁碾过

1. **模型厂自带评测**（OpenAI Evals、DashScope 评测、Braintrust/LangSmith/Langfuse/Arize）。
   他们离数据更近、离付费入口更近。**我们唯一守得住的差异是「跨厂商中立」**——
   一旦被认为是某家的附庸，价值归零。这反过来说明
   `JUDGE_MODELS` 跨家族池不是技术选项，而是**商业生命线**。
2. **GDPval 的公开评分服务**。OpenAI 已经开源 220 题 gold 子集并提供自动评分[2](https://openreview.net/forum?id=hcuEdq6eKD)。
   免费 + 权威 + 覆盖 44 职业。我们的 12 道题在它面前毫无规模优势。
   **不要在「题多」上竞争，要在「题贴合你的工作流」上竞争。**
3. **咨询公司**。企业选型这件事，德勤们会用人力做，收 50 万，
   而且客户觉得更放心。我们必须比人便宜一个数量级且快一个数量级。

### 3.4 商业模式上尚未验证的假设（每条都要做实验证伪）

| # | 假设 | 现状 | 怎么证伪 |
|---|---|---|---|
| H1 | 有人愿意为「Agent 准入报告」付费 | 完全未验证 | 拿现在的报告样例去问 10 个企业 AI 负责人：「这份报告值多少钱？」 |
| H2 | 评测结论能改变实际选型决策 | 未验证 | 在真实选型场景里跟踪：用户最后选的是不是榜首？不是的话为什么？ |
| H3 | 使用者愿意做人工抽检（元评估的数据来源） | 未验证，且**这是整个可信度体系的地基** | 观察抽检按钮的实际点击率。若 <5%，元评估就是空转 |
| H4 | 主观榜（个人权重）真的产生不同排序 | **可以立刻算** | 用现有数据算：不同权重下 Top-1 变化的比例。若 <20%，主观榜就是伪需求 |

**H4 我强烈建议本周就做**，它只需要跑几行脚本，却能决定
「双榜」这个核心叙事到底成不成立。如果不同人的权重算出来 Top-1 都一样，
那「每个人有自己的最佳数字员工」这句话就是错的，整个产品叙事要重写。

### 3.5 企业客户会问、而我们现在答不上来的问题

按被问到的概率排序：

1. **数据去哪了？** —— 部分能答（本地优先、PostHog 需显式 key）。
   但 `AGENTCORP_REACTIONS_API` 跨用户聚合一旦启用就出网，需要 DPA 与数据流向图。
2. **私有化部署怎么做？** —— 目前是 Electron 桌面应用。
   企业要的是 Docker Compose / K8s + SSO + 审计日志。**这是一次架构级改动。**
3. **多人协作？** —— 完全没有。评测结果存在个人机器上，团队看不到。
4. **能接我们自己的 Agent 吗？** —— 只能接 OpenClaw gateway 兼容的。
   接 Coze / Dify / 扣子 / 自研 HTTP Agent **目前都不行**。
   这是最大的集成缺口：`candidate_runner.py` 有抽象层但只实现了两个通道。
5. **审计与合规**：评测记录能导出吗、能防篡改吗、留存多久？（见持久化设计文档）
6. **沙盒在我们机器上跑候选代码，安全责任谁的？** —— 现在只有进程级限制，
   没有容器隔离。企业安全团队会直接卡住。

### 3.6 法务与许可（被忽略但可能致命）

- `resources/marketplace/` 里 285 个 agent 模板的来源与许可**没有说明**。
  如果其中有从他人仓库搬来的 prompt/persona，商业化时是隐患。
  **建议立刻做一次来源审计，并在仓库里加 `resources/marketplace/PROVENANCE.md`。**
- 项目 fork 自 ClawCorp/OpenClaw（MIT），依赖里锁着 `openclaw@2026.3.22`、
  `@larksuite/openclaw-lark`、`@tencent-weixin/openclaw-weixin` 等。
  **上游一旦变更许可或停更，我们的桌面壳会失去维护**。
  需要评估：能否把评测内核与桌面壳解耦，让内核独立可用？（见 Roadmap P1）
- GitHub 导入功能抓取的仓库元数据，展示时要标注来源与许可（已实现 license 字段）。

## 第四部分 · 唯一能把项目从玩具变成科学的实验

如果这份文档你只看一节，请看这节。

### 4.1 预测效度验证（Predictive Validity Study）

**研究问题**：AgentCorp 的准入评分，能否预测该 agent 在后续真实任务中的表现？
个性化权重是否比群体平均权重预测得更准？

**设计**：前瞻性队列研究（prospective cohort），不是回溯拟合。

```
T0（准入）: 对 N 个 agent × M 个使用者，跑完整评测 → 得到
            - 客观分 S_obj（群体一致）
            - 个性化分 S_fit(u)（按使用者 u 的权重）
T1..T4（4 周）: 使用者在真实工作中派活给这些 agent，
            系统自动记录：完成率、返工轮数、人工干预次数、
            实际成本、以及每次交付后的 1–5 分满意度
T5（分析）: 计算 Spearman ρ(S, 真实表现) 与 ΔAUC
```

**主要终点**：
- H_A1：`ρ(S_obj, 真实完成率) > 0`（准入分有效）
- H_A2：`ρ(S_fit(u), 满意度_u) > ρ(S_obj, 满意度_u)`（**个性化有增量价值** ← 这才是我们的贡献）

**样本量（这是最关键的、也是最容易被忽略的数字）**：

按 Fisher z 变换，双侧 α=0.05、power=0.8：

| 想检出的效应 | 需要的配对样本数 |
|---|---|
| ρ = 0.5（强） | **n ≈ 29** |
| ρ = 0.4（中等） | **n ≈ 47** |
| ρ = 0.3（弱但有意义） | **n ≈ 85** |

一个「配对样本」= 一个 (agent, 使用者, 任务) 三元组的完整记录。
若每位使用者用 5 个 agent、每周 4 个任务，则
**10 位真实使用者跑 4 周 ≈ 200 个配对样本**，足以检出 ρ=0.3 的效应。

**这就是全部门槛：10 个真实用户、4 周。** 不需要资金、不需要 GPU、
不需要发论文的关系网。这件事做完，AgentCorp 就有了别人没有的东西：
**一份把准入评分与真实表现配对起来的数据集**。做不完，它就永远是个 demo。

**避免循环论证的纪律**：
- T1–T4 的真实表现评价**不能用同一个 LLM 裁判**产生，否则是自己验证自己。
  完成率/返工/干预次数是客观计数；满意度必须由人打。
- 使用者在 T1–T4 期间**不应看到 T0 的评分**（避免预期效应）。
  这需要一个「盲测模式」开关——**当前代码没有，需要加**。

### 4.2 立刻能做的两个低成本实验（本周）

**实验 A · 题库信度（成本：几十元 API 费）**
把 4 道 code 题拆成两半，同一批 agent 各做一半，算两半分数的相关。
若 Spearman ρ < 0.5，说明题量严重不足，必须先扩题库再做别的。

**实验 B · 主观榜是否真的分化（成本：0，纯计算）**
用 5 组典型权重（重质量 / 重成本 / 重速度 / 重可靠 / 均衡）
对同一批候选算 user_fit，统计 Top-1 的重合率。
若重合率 > 80%，「双榜」叙事需要重写。

## 第五部分 · Roadmap

### Phase 0 · 赛期（现在 → 2026-09，约 4 周）

目标：**把「诚实 + 可核验」这个差异化讲透，不再增加新功能。**

| 优先级 | 事项 | 验收标准 |
|---|---|---|
| P0 | 跑实验 A（题库信度）与实验 B（主观榜分化） | 有两张图 + 一段结论，无论结果好坏都写进 README |
| P0 | 一键安装：把 model-service 打进 Electron 或提供 Docker 一行命令 | 从零到跑完一次评测 < 5 分钟，无需手工配环境变量 |
| P0 | 首屏改为「描述你的工作」而不是 Chat | 新用户 3 步内看到第一个评测结论 |
| P1 | 演示脚本彩排 + 8 分钟录屏 | 重点放在「测试全绿但扫描抓出 3 处高危」这个反差 |
| P1 | `resources/marketplace/PROVENANCE.md` 来源与许可审计 | 每个模板都有来源标注 |
| P2 | 榜单/报告的 Markdown 导出（持久化设计文档 §4 的子集） | 能生成一份可贴进周报的报告 |

**明确不做**：不新增评测维度、不做移动端、不做多人协作。

### Phase 1 · 学术验证（2026-09 → 2026-12，3 个月）

目标：**产出别人没有的数据，而不是别人也有的功能。**

| 事项 | 说明 | 产出 |
|---|---|---|
| 招募 10–15 位真实使用者 | 从 B 类 ICP（Agent 开发者）里找最容易，他们有动机 | 用户名单 + 知情同意 |
| 实现「盲测模式」 | T1–T4 期间隐藏准入评分 | 一个 feature flag |
| 落地持久化（`docs/design/persistence-and-report-export.md`） | 没有它就没有时间序数据，实验做不了 | SQLite + 历史端点 |
| 运行 4 周前瞻性队列 | 见 §4.1 | ≥200 配对样本 |
| 扩题库：每工种 4 → 10 题，其中 4 题永不公开 | 同时解决信度与污染 | 30 题题库 + held-out 子集 |
| 修收敛层编码器 | 词袋哈希 → 真实句向量（可用裁判模型的 embedding 接口） | 同义改写一致性测试通过 |
| 撰写论文 | 目标：CHI / CSCW（人机协作角度）或 EMNLP Industry Track | 一篇投稿 |

**为什么建议投 CHI/CSCW 而不是 NeurIPS**：我们的贡献本质是
**「人如何与评测系统共同做出选型决策」**，是 HCI 问题不是 ML 问题。
在 NeurIPS 我们和 GDPval 硬碰硬会输；在 CHI，
「个体价值排序如何影响 Agent 选型」是一个几乎没人做的新题。

**Phase 1 的成败判据（诚实设定）**：
- 若 H_A1 成立（准入分能预测真实表现）→ 进入 Phase 2；
- 若 H_A1 不成立但 H_A2 成立（个性化有增量）→ 缩小定位为「个性化匹配工具」；
- 若两者都不成立 → **公开发表负面结果，并把产品转型为纯粹的
  「Agent 试用工作台」**（提供沙盒执行与证据留痕，不再声称能预测）。
  这个分支不丢人，反而是这个项目最有价值的可能结局之一。

### Phase 2 · 商业验证（2027-01 → 2027-06）

前提：Phase 1 的 H_A1 或 H_A2 成立。

| 事项 | 验收 |
|---|---|
| 架构解耦：评测内核脱离 Electron，可 Docker 部署 | `docker compose up` 能起完整服务 |
| 候选接入层扩展：Coze / Dify / OpenAI-compatible / MCP Server 四种通道 | 每种通道有集成测试 |
| 沙盒容器化（gVisor / Firecracker / 至少 Docker + seccomp） | 通过一次外部安全评审 |
| 多人协作与审计：SSO、角色、不可篡改的评审记录 | 能通过一家企业的安全问卷 |
| 与 3 家企业做付费 POC | 每家 ¥3–10 万，验证 H1 |

### Phase 3 · 规模化（2027 下半年起）

只有 Phase 2 的 POC 有复购才启动。核心是**数据飞轮**：
题库 + 各行业准入基线 + 准入分与真实表现的配对数据集。
到那时软件本身不再是护城河，**数据是**。

## 第六部分 · 我认为你现在最应该做的三件事

1. **本周做实验 B**（主观榜是否真的分化）。零成本，但它直接决定核心叙事成不成立。
   如果不成立，越早知道越好。
2. **做一次定位决策：B 端主线还是 C 端主线。** 这两条路的产品形态、
   架构、话术完全不同，同时做等于都做不好。我的建议是 B 端主线，
   但这是你的判断，不是我的。
3. **给自己设一个 Phase 1 的 kill criteria 并写下来。**
   例如：「如果 2026 年 12 月前拿不到 200 个配对样本，就把项目开源归档、
   写一篇复盘。」有退出条件的项目才是项目，没有的是执念。
