# 双轨定位：企业 Agent 治理 ＋ 个人工作流选型

> 面向问题：场景只讲「企业治理数字员工」会不会太窄？能不能同时覆盖普通职场人？
> 结论：**能，而且不是硬凑——两者共用同一套引擎，差别只在「谁是那个老板」。**
> 这个统一点在代码里已经存在（`BossProfile`），不是为了讲故事新造的概念。

---

## 一、为什么可以统一：一个技术事实

AgentCorp 的评估不是「给 Agent 打一个绝对分」，而是「给 **某个特定的人** 打一个契合分」。
这件事在代码里由两个机制实现：

**机制 1 · BossProfile（评估视角注入）** — `src/stores/bossProfile.ts` + `judgeClient.buildPersonaPreamble`

裁判 prompt 里会注入一段「评估上下文 · 老板原型」，让裁判从
「与**这样一位**老板协作」的视角评估 Agent：

```
- 领域：合规/金融
- 经验水平：expert
- 风险偏好：high
- 沟通风格：detailed
- 约束偏好：safety、quality
```

同一个 Agent，换一个 BossProfile，分数就会变。**这就是个性化评估。**

**机制 2 · userWeight（权重个性化）** — `src/engine/marketplace/userFit.ts`

```
effWeight = normalize( userWeight[d] × dimBoost[d] )
userFit   = Σ_d (radar[d]/5) × effWeight[d]
```

`userWeight` 可由用户在双榜上**拖拽重排回灌**（设计 §7.3 通道 A）。
有人认为「保住完成度比省时间重要」，有人相反——系统不假装存在唯一最优解。

> **关键洞察：`BossProfile` 里的「老板」从来就不必是一家公司。
> 它是「使用并为结果负责的那个人」。企业场景里它是管理者，个人场景里它就是你自己。**
>
> 换句话说：**企业治理与个人选型不是两个产品，是同一个引擎的两种 BossProfile 实例化。**

## 二、两轨的具体形态

| | **轨道 A：企业 Agent 治理** | **轨道 B：个人工作流选型** |
|---|---|---|
| 「老板」是谁 | 团队负责人 / 平台治理方 | 职场人自己 |
| 任务输入 | Agent 准入工单（可由 Jira/ServiceNow 触发） | 「我想找个能帮我干 X 的 Agent」 |
| 关心什么 | 能不能上线、出事谁负责、有没有审计证据 | 顺不顺手、省不省时间、值不值这个钱 |
| 用哪些 Agent | 全部 4 个（Boss/Dispatcher/Recruiter/Evaluator） | 同样 4 个，但 Boss = 用户本人 |
| 审批门 | 强制人工确认 + 审计流水 + 回滚 | 降级为「要不要采纳」的一次确认 |
| 评分侧重 | reliability / cost 权重高（企业怕出事、怕超预算） | task / comm 权重高（个人怕不好用、怕沟通累） |
| 结果落点 | 准入台账 + 合规审计记录 | 个人 Agent 工具箱 + 复用偏好 |
| 已有实现 | `approvalGate.ts` / `a2a-trace` / 双榜 | `BossProfile` / `userWeight` / 小红心 / 主观榜 |

**同一套代码支撑两轨的证据**：
- 六维雷达 + craft 维：两轨共用（`registry.ts`）
- pass^k + 偏差审计：两轨共用（可靠性对个人同样重要——「每次都行」才敢依赖）
- 双榜设计（客观榜 + 主观榜）：**本来就是为「不存在唯一最优解」设计的**，
  客观榜服务企业合规，主观榜服务个人偏好
- 审批门：`requiresApproval` 是 RoleCard 上的字段，个人场景把风险阈值调低即可，不需改代码

## 三、怎么讲，才不显得摇摆

参赛最忌讳「什么都能做」——评委会认为你没想清楚。所以**讲法要有主次**：

### 推荐叙事结构（GOAI 初赛用）

> **主场景（打赛道）**：企业 Agent 准入与协同治理。
> 这是 Agent Infra 赛道要的「企业级复杂任务」「行业普遍性」「安全审计」。
>
> **底层主张（讲差异化）**：我们不相信存在「客观最好的 Agent」，
> 只存在「对某个具体的人/组织最合适的 Agent」。所以评估层的一等公民是 `BossProfile` ——
> 评估视角本身是参数。
>
> **由此自然延伸（讲想象空间，一页带过）**：把 BossProfile 从「企业管理者」
> 换成「个人职场人」，同一套引擎就变成个人的 Agent 选型助手。
> **企业版和个人版不是两个路线图，是同一个引擎的两个实例。**
> 这也是为什么我们的开源价值不止于企业内网——评估层可以被任何人复用。

这样讲的好处：
1. **主线清晰**：赛道要什么给什么，不失焦。
2. **差异化立住**：「评估视角是参数」这个主张，比「我们有个评估系统」有力得多。
3. **想象空间打开**：评委会看到 TAM 不止企业市场，但不会觉得你在摇摆——
   因为你论证了这是**同一个技术内核的自然外延**，而不是两个并列的赛道。

### 一句话版本（放在作品简介和封面页）

> **「不做 Agent 的通用排行榜，做『对你而言最合适』的判断依据——
> 无论这个『你』是一家公司，还是一个想找对工具的普通人。」**

## 四、对 PPT 的具体建议

- **第 2 页（问题）**：两个人物场景并排，但企业侧放大：
  - 左（主）：技术负责人要引入外部 Agent，无法回答「能不能上线、出事谁担责」
  - 右（次）：产品经理想找个写周报的 Agent，只能看 star 数和别人一句「挺好用」
  - 一句收口：**「这两个问题的数学形式是同一个：在缺乏可信证据的情况下做选型决策。」**

- **第 11 页附近加一个小节**：「同一引擎的两种实例化」——
  放 BossProfile 注入前后同一 Agent 分数变化的对比（这个 demo 你现做也来得及，
  `judgeChat` 已支持传 persona）。**这是最有说服力的一张图**：
  同一个 Agent，风险厌恶老板给 3.2 分，成长型老板给 4.1 分。

- **末页路线图**：企业版（合规审计 / 私有部署）与个人版（轻量 Web / 工具箱）
  画成同一棵树的两个分支，根是「评估内核」。

## 五、风险提示

**不要在初赛把个人版讲成同等权重的第二主场景。** 理由：

- 赛道名字叫「Agent Infra 新智基座」，明确要求「企业级复杂任务」「不少于 3 个职能 Agent 的
  完整闭环」「安全审计」。个人版天然弱化审批、审计、多 Agent 协同——
  讲太重会显得你在偏离赛道。
- 个人版讲成「延伸场景 + 开源复用价值」是加分；讲成「我们也做 to C」是减分。

**建议配比：企业主线 85%，个人延伸 15%（1 页 + 作品简介一句）。**
