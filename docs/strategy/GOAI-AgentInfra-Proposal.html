场景与价值 01

企业选 Agent，今天靠的是什么？

选型前：没有依据

能看到的只有 star 数、README 写得好不好、同事一句「挺好用」。

个人开发者上传的 Agent 天生 0 star——能力强弱与可见度完全脱钩。

运行中：没有证据

任务交出去了，但说不清是谁拖慢的、返工了几次、烧掉多少 token。

多 Agent 委派链路一旦超过两层，责任归属就靠猜。

复盘时：没有沉淀

这次踩的坑，下次换个人重踩一遍。

选错的代价由业务承担，而经验没有留在系统里。

为什么这是「企业级复杂任务」而非单点问题

多源异质输入
候选来自 GitHub、内部仓库、个人上传；产出横跨代码、图像、文案、语音。

结果难验证
「写得好不好」没有单一标准答案，需要工种差异化的验收口径。

证据须留痕
选型结论要能被复查、被追问、被审计，否则无法进入企业决策流程。

我们的定位不是「再做一个 Agent」，而是做 Agent 进入生产前的那道评估与准入基础设施。

方案设计 02

把「评测」实现为四职能 Agent 的端到端闭环

评测不是一次模型调用，而是一条需要拆解、协同、验证、留痕的流水线。 我们按职能把它拆成四个身份清晰的 Agent。

① 招聘 Agent 候选聚合 + 输入侧安全审查

GitHub URL / 上传包 → 规范化 profile

② 面试官 Agent 工种差异化小任务评测

LLM-as-judge → 六维雷达 + evidence

③ 绩效审计 Agent 委派轨迹客观核算

A2A trace → 完成度 / 返工 / 耗时 / token

④ 复盘 Agent 经验沉淀为可复用能力

结论 → Skill + 知识条目

为什么必须是多 Agent，而不是一个大 prompt

  • 职责隔离即安全边界：面试官只读沙箱产出，不碰生产环境；审计只算不排序。
  • 结论不由生成方自评：客观指标全部由审计 Agent 从轨迹算，不采信被评方自述。
  • 失败可定位：四段各有输入输出契约，出错能指到具体环节而非「模型不行」。

人始终在环中

  • 客观榜给可比基线，主观榜允许每个用户按自身价值观重排。
  • 有人认为保完成度比省时间重要，有人相反——我们不假设存在唯一最优解。
  • 偏好回灌下一轮打分，把模糊需求逐步收敛为可检验目标。

方案设计 03 · Agent Identity

四个 Agent 的身份属性与能力边界

Agent职能定义输入输出能力边界（不做什么）协同关系
招聘 Agent
recruiter		 聚合候选来源，做输入侧安全审查与去重，产出规范化档案 GitHub 仓库 URL、本地上传包、个人 Agent 声明 AgentProfile（能力声明、依赖、来源可信度标记） 不做能力判断、不打分、不执行候选代码 上游入口；产出交面试官
面试官 Agent
interviewer		 按工种派发差异化小任务，以 LLM-as-judge 评分并留证据 profile + 工种 Task-Set + 用户偏好权重 六维雷达（含 craft 维）、user_fit、evidence_trace 不碰生产环境、不写工作区、不采信候选自述 消费招聘产出；评分交审计交叉核对
绩效审计 Agent
auditor		 从真实委派轨迹确定性核算客观指标，生成可比榜单 A2A trace、会话运行时状态、任务看板记录 完成度 / bug 数 / 耗时 / 返工次数 / token 成本 + 客观榜 不做主观排序、不调 LLM 产出分数（纯确定性计算） 横向校验面试官结论；异常回退面试官重跑
复盘 Agent
retrospector		 汇总三方结论与人工修正，沉淀为可复用 Skill 与知识条目 上三者产出 + 用户主观榜调整记录 Skill 定义、复盘报告、下轮任务集修订建议 不自动改线上配置、不越过人工确认写入 闭环末端；产出回灌招聘与面试官
每个 Agent 有独立身份、独立工具权限范围与独立失败处理路径。 完整字段清单按参赛手册附录 A 格式另附。

方案设计 05 · 闭环

八段闭环：从任务输入到经验沉淀

① 任务输入

候选 Agent 导入请求、真实业务任务、历史评测重跑请求。

② 任务拆解

leader 按工种与评测阶段拆分，派发给招聘 / 面试官 / 审计。

③ 上下文传递

逐跳 trace 记录委派者、被委派者、轮次、摘要与工具结果。

④ 工具调用

经 Host API 契约层调用裁判服务、仓库解析、指标计算。

⑤ 结果验证

审计 Agent 以确定性算法交叉核对面试官评分，偏差超阈值触发重跑。

⑥ 证据沉淀

Trace / 评分证据 / 运行指标 JSONL 落盘，评分可回溯到具体输出片段。

⑦ 审批与回滚

导入外部仓库、写入工作区等高风险动作需人工确认；失败状态可回退重派。

⑧ 经验沉淀

Skill 与工具集成 06

核心 Skill 清单（赛道必选项）

Skill 是任务能力抽象层，而非一次性 Agent 行为描述。以下四个 Skill 可脱离本产品， 在任意 Agent 系统中独立调用。

Skill用途输入 / 输出 调用条件依赖工具 失败处理安全边界与复用价值
safe-agent-import 外部 Agent 仓库安全导入与规范化 入：仓库 URL / 包
出：AgentProfile + 风险标记		 招聘 Agent 收到新候选时 Git 解析、路径校验、清单解析 校验不通过即拒绝导入并返回具体原因，不做静默降级 路径穿越 / 协议白名单 / 尺寸上限 / 不执行候选代码。
复用：任何需要引入第三方 Agent 的系统都需要这道门。
role-based-eval 工种差异化能力评测 入：profile + 工种 + 任务集
出：六维分 + evidence		 候选通过导入校验后 裁判模型服务、沙箱执行器 模型不可用返回 503 并标记 degraded，不产出伪造分数 沙箱内执行、只读工作区、超时强制中止。
复用：可作为通用 Agent 能力基准测评组件。
trace-audit 委派轨迹客观指标核算 入：A2A trace
出：完成度 / 返工 / 耗时 / 成本		 任务执行结束或阶段性汇总时 Trace 存储、任务看板读模型 trace 缺失时返回 insufficient_evidence 而非补零 纯读取、纯确定性计算、不调用 LLM。
复用：任何多 Agent 系统的责任归属与成本归因。
retro-distill 复盘结论沉淀为可复用知识 入：评测结论 + 人工修正
出：知识条目 + 任务集修订		 一轮评测闭环完成后 知识存储、Skill 注册表 写入冲突时保留双版本待人工裁决，不自动覆盖 不自动改线上配置、写入需人工确认。
复用：把一次性经验变成组织资产。
与多 Agent 流程的关系：四个 Skill 与四个 Agent 并非一一绑定—— trace-audit 同时被审计与复盘调用，role-based-eval 可被外部系统直接调用而不经过我们的编排层。 这是 Skill 作为能力抽象层、而非 Agent 行为脚本的体现。

Skill 与工具集成 07

工具集成契约：未用 MCP 的等价方案

我们当前采用自有契约层完成工具接入。按赛道 2.2 要求，逐项说明协议、鉴权、 Schema、错误处理、审计与迁移成本。

调用链路

渲染层 hostApiFetch
  ↓ IPC hostapi:fetch
主进程代理（唯一持有凭据）
  ↓ HTTP 127.0.0.1
本地服务 → 外部工具 / 模型

  • 协议：JSON over HTTP，SSE 承载流式事件
  • 鉴权：凭据仅存于主进程，渲染层无法读取；本地服务绑定回环地址
  • 幂等：评测请求带 run_id，重复提交返回既有结果而非重跑

契约要素

  • Schema：请求与响应类型在前后端严格镜像，契约变更须两侧同步
  • 错误处理：错误以异常抛出而非静默返回空值；模型不可用返回 503 并携带原因
  • 权限范围：每个工具声明可访问路径与网络范围，超出即拒绝
  • 失败重试：读操作幂等可重试；写操作不自动重试，交人工确认
  • 审计日志：调用方、参数摘要、耗时、结果状态逐条落盘
  • 降级方式：裁判服务不可用时评测标记 degraded 并暂停，不用启发式分数顶替

迁移到 MCP 的成本评估

我们的工具调用已经收敛到单一代理入口，工具能力以「名称 + 参数 Schema + 权限范围 + 返回结构」四元组声明。 迁移到 MCP 只需在主进程代理层增加协议适配器，把现有工具声明翻译为 MCP tool descriptor—— 调用链路、鉴权模型、审计埋点均不需重新设计。这是我们选择先做契约收敛、再谈协议对接的原因。

工程能力 08

可观测：让评测结论可回溯、可追问

采集方式与数据类型

  • Trace：每次委派逐跳写入 JSONL——委派者、被委派者、轮次、任务状态、返工关联、渠道、发起与完成时间、摘要
  • Metrics：任务完成度、返工次数、端到端耗时、token 消耗与成本
  • Log：工具调用审计（调用方、参数摘要、耗时、结果状态）

存储：按根会话聚合落盘，评估阶段按 run_id 加载对应轨迹集合。

应用场景与效果

  • 客观指标去自评化：返工次数由 rework_of 关联链计数得出，而非模型自述「我返工了 2 次」
  • 责任归属：多层委派下能定位到具体是哪一跳阻塞、耗时多少
  • 离线评估：同一批轨迹可反复重算指标，支持评分口径调整后的历史回溯

诚实说明

当前 Trace 采用自有 schema，尚未对齐 OpenTelemetry GenAI 语义规范。 我们的字段（delegator / delegatee / round / state）与 GenAI span 属性存在概念对应关系， 复赛阶段计划补充语义映射层以支持标准化后端接入。此处不夸大为「已遵循标准」。

工程能力 09

异常分支、安全边界与风险控制

输入侧：不可信来源

  • 仓库地址协议白名单，拒绝非预期协议
  • 解压与写入路径校验，阻断路径穿越
  • 体积与文件数上限，防解压炸弹
  • 导入阶段绝不执行候选代码

执行侧：评测过程

  • 候选产出在沙箱内生成，工作区只读
  • 超时强制中止并标记，不无限等待
  • 裁判模型不可用 → 返回 503 标记 degraded
  • 宁可不出分，不出假分

落盘侧：旁路容错

  • Trace 写入失败不阻断主流程
  • 派发 / 干预 / 中止照常返回
  • 但对应指标标记为证据不足
  • 可观测性故障不应放大为业务故障

高风险动作的人工确认与回滚

  • 导入外部仓库、写入工作区、变更团队编排——均需人工确认
  • 任务阻塞与待审批状态向上冒泡：任一成员阻塞，团队状态即为 blocked
  • 复盘写入冲突时保留双版本待人工裁决，不自动覆盖

元评估风险：用模型评模型

  • 风险：裁判模型自身偏好会污染结论，且难以自证
  • 缓解一：客观指标完全不经 LLM，由轨迹确定性计算
  • 缓解二：评分附 evidence_trace，可回溯到具体输出片段供人工抽检
  • 缓解三：主观榜由人重排，模型结论不是终审
  • 我们的立场：这是缓解而非消除，不宣称已解决

我们选择明确标注而非模糊表述——评审可据此判断哪些是既成事实，哪些是计划。

落地计划与开源开放

第一阶段 · 打通真实评测

  • 接通裁判模型真实推理，替换现有启发式打分
  • 三类工种任务集与结构化评分契约

第二阶段 · 能力抽象与协同

  • 四个 Skill 拆分为独立可调用单元并发布契约文档
  • AgentTeams 框架本体接入，替换自有编排入口
  • Trace 语义映射到 OpenTelemetry GenAI

验收：Skill 可被本产品之外的系统直接调用并产出一致结果。

第三阶段 · 知识沉淀闭环

  • 复盘知识库与检索增强接入
  • 偏好回灌形成完整收敛回路
  • 跨组织匿名基准数据集

验收：第二轮评测能复用第一轮沉淀，任务集自动修订生效。

开源与复用计划

  • 协议：MIT，代码仓库公开
  • Skill 独立开放：四个 Skill 附完整输入输出契约，可脱离本产品使用

  • 裁判后端可替换：不绑定单一模型或单一硬件
我们希望留下的不只是一个产品，而是一套「Agent 该怎么被评测」的可复用工程约定。
